# Технічна документація

## 1. Призначення і межі компонента

`Code.gs` — bound Google Apps Script для майстер-таблиці Google Sheets. Він має дві незалежні відповідальності:

1. щоденний перенос придатних основних рядків до гарантійного перечеку;
2. резервна ручна фіналізація одного гарантійного рядка через встановлений `onEdit`-тригер.

Перевірка донорів, Telegram-взаємодія, робочі кола, резерв `H → S` і клієнтський звіт не реалізовані в цьому файлі.

## 2. Публічні точки входу

| Функція | Виклик | Призначення |
| --- | --- | --- |
| `WR_setupWarrantyAutomation_v1()` | вручну після встановлення або відновлення | Перестворює власні тригери та створює журнал |
| `WR_runDailyTransfer_v1()` | щоденний time-based trigger або ручний запуск | Обробляє всі придатні рядки видимих листів «Морда» |
| `WR_installedOnEdit_v1(e)` | installed onEdit trigger | Реагує на ручне встановлення `Перечек готово` в одній клітинці гарантійного листа |

Імена публічних функцій є частиною контракту з тригерами й не повинні змінюватися без міграції тригерів.

Внутрішні функції ізольовано в `WR_WarrantyRecheckAutomation_v1` через IIFE. Скрипт не створює `onOpen` і не оголошує простий глобальний `onEdit`.

## 3. Конфігурація

Основні значення зберігаються в `WARRANTY_CFG`:

| Параметр | Значення | Значення для логіки |
| --- | --- | --- |
| `headerRow` | `1` | Рядок заголовків у майстрі та перечеку |
| `mainPrefix` | `Морда` | Префікс основних листів |
| `warrantyPrefix` | `Перечек по гарантії` | Префікс гарантійних листів |
| `eligibleMainStatuses` | `прийнято`, `перевірено` | Допустимі статуси джерела після нормалізації |
| `needsReplacementStatus` | `Потрібно зробити заміни` | Початковий статус у перечеку |
| `readyStatus` | `Перечек готово` | Статус резервного ручного завершення |
| `warrantyDays` | `14` | Затримка до переносу після дедлайну |
| `replacementDays` | `7` | Додатковий строк замін після дати переносу за правилом |
| `tzHeaderScanRows` | `10` | Глибина пошуку заголовків у робочому ТЗ |
| `logSheet` | `_Warranty log` | Назва прихованого журналу |

Фактична формула кінцевого строку: `deadline + warrantyDays + replacementDays`, тобто дедлайн + 21 день. Вона не залежить від дати фактичного запуску.

## 4. Контракт аркушів і колонок

`headerMap_()` читає перший рядок до `getLastColumn()` і будує map за нормалізованими заголовками. `norm_()`:

- перетворює значення на рядок;
- обрізає краї;
- переводить у нижній регістр;
- стискає послідовності пробілів до одного.

### Основний лист

Обов’язкові колонки:

- `ТЗ замовника`;
- `Перевірка`;
- `Дедлайн` або `Deadline`;
- `№`, `No` або `Номер`;
- `Коментар Аня`.

### Гарантійний лист

Обов’язкові колонки:

- `ТЗ замовника`;
- `Перевірка`;
- `End data` або `End date`;
- `№`, `No`, `Номер` або `l`;
- `Коментар Аня`.

Літери й порядок колонок не фіксовані.

## 5. Розпізнавання листів

`parseSheetMonth_()` приймає назви, що після нормалізації відповідають:

- `Морда <суфікс>` або `Морда - <суфікс>`;
- `Перечек по гарантії <суфікс>` або `Перечек по гарантії - <суфікс>`.

Звичайні, короткі й довгі тире нормалізуються до `-`. Регістр і надлишкові пробіли не впливають.

`activeMainSheets_()` відбирає лише видимі основні листи. Сортування за відносною відстанню від поточного місяця впливає на порядок обробки, але не обмежує обробку поточним і попереднім місяцями.

Цільовий місяць кожного кандидата обчислюється з дедлайну через `Utilities.formatDate(..., tz, 'M')` і `WARRANTY_MONTH_NAMES`.

## 6. Алгоритм щоденного переносу

`runDailyTransfer()` виконується під document lock:

1. відкриває активну таблицю;
2. нормалізує поточну дату до початку дня в часовому поясі таблиці;
3. отримує всі видимі основні листи;
4. створює кеш `warrantyContexts` на один запуск;
5. передає кожний лист у `transferEligibleRows_()`.

Для кожного рядка нижче заголовка перевіряються умови:

1. дедлайн розпізнано як дату;
2. `today >= startOfDay(deadline) + 14 днів`;
3. нормалізований статус є в `eligibleMainStatuses`;
4. номер не порожній;
5. номер не відповідає `/\/\s*\d+\s*$/`;
6. сформовано непорожній ключ ТЗ.

Для кожного кандидата:

1. `warrantyContext_()` знаходить або створює гарантійний лист;
2. ключ порівнюється з `existingKeys` цільового листа;
3. рядок копіюється в `nextRow`;
4. статус встановлюється в `Потрібно зробити заміни`;
5. `End data` встановлюється в `deadline + 21 день` з форматом `dd.MM.yyyy`;
6. ключ додається до кешу, а `nextRow` збільшується;
7. журнал отримує `TRANSFER`.

Помилка одного кандидата перехоплюється й записується як `ERROR`; інші кандидати продовжують оброблятися.

## 7. Формування ключа ТЗ і захист від повтору

Джерело URL перевіряється в такому порядку:

1. URL у RichText клітинки;
2. URL в окремому RichText run;
3. перший аргумент формули `HYPERLINK`;
4. перший `http://` або `https://` у відображуваному тексті.

`normalizeUrl_()` використовує ID між `/d/` і наступним роздільником для Google-файлів. Тому різні `gid` того самого файла дають однаковий ключ. Для інших значень видаляються query/fragment і кінцевий `/`, після чого рядок переводиться в нижній регістр.

Перевірка повтору виконується лише в цільовому гарантійному листі. Інші місяці та інші файли не скануються.

## 8. Створення гарантійного листа

`ensureWarrantySheet_()` повертає наявний лист цільового місяця або створює новий.

Вибір шаблону в `findWarrantyTemplateSheet_()`:

1. збирає всі листи, що відповідають гарантійному префіксу;
2. для відомого місяця шукає найближчий наявний місяць із номером, не більшим за цільовий;
3. якщо такого немає — бере останній гарантійний лист у порядку книги.

Після `copyTo()` новий лист:

- отримує назву `Перечек по гарантії - <Місяць>`;
- робиться видимим;
- очищує content і notes нижче першого рядка до `getLastRow()` у межах `getMaxColumns()`;
- зберігає структуру та форматування шаблону;
- реєструється як `SHEET_CREATE`.

Логіка працює з назвами місяців без року. Таблиці, де в одному файлі одночасно присутні однакові місяці різних років, потребують окремого дизайну.

## 9. Копіювання рядка

`copyMappedRow_()` створює план за збіжними нормалізованими заголовками.

Особливості:

- `End data` не копіюється, бо обчислюється заново;
- номер і `Коментар Аня` мають явні mapping-и;
- суміжні source/destination-колонки групуються в один `copyTo()`;
- використовується `SpreadsheetApp.CopyPasteType.PASTE_NORMAL`;
- висота цільового рядка прирівнюється до висоти джерела.

Після копіювання `Перевірка` переписується. Якщо її клітинка має validation типу `VALUE_IN_LIST`, `ensureListValidationValues_()` додає два потрібні статуси, не видаляючи наявні значення. Інші типи validation не перебудовуються.

## 10. Резервний installed onEdit

`installedOnEdit(e)` негайно завершується, якщо:

- немає event/range;
- змінено більше однієї клітинки;
- лист не є гарантійним;
- змінено не колонку `Перевірка` або заголовок;
- нове значення не дорівнює `Перечек готово` після нормалізації.

За валідної події `finishWarrantyRow_()`:

1. отримує URL і ключ ТЗ з гарантійного рядка;
2. сканує всі основні листи, включно з прихованими;
3. вимагає рівно один збіг ключа;
4. викликає `stampExternalBrief_()`;
5. тільки після успішного оформлення ТЗ змінює основний статус на `Перечек готово`;
6. пише `READY`.

`stampExternalBrief_()` відкриває файл за URL, але використовує `getSheets()[0]`, тобто перший лист незалежно від `gid` у URL. Серед перших десяти рядків він шукає `Donor` та `Text`/`Date` в одному рядку.

Після знаходження:

- заголовок text/date-колонки стає `Date`;
- вміст цієї колонки до останнього використаного рядка очищується;
- клітинки навпроти зеленого `Donor` отримують поточну дату;
- діапазон форматується як `dd.MM.yyyy`.

Зелений колір визначається евристикою RGB: `g >= 90`, `g >= r + 10`, `g >= b + 10`.

## 11. Обробка помилок onEdit

Зовнішній `try/catch` намагається:

1. повернути `e.oldValue`, а якщо його немає — `Потрібно зробити заміни`;
2. додати до клітинки note `Автоматизація не завершена: ...`;
3. записати `ERROR`.

Успішний запуск очищує note клітинки.

Це не транзакційний rollback. Якщо зовнішнє ТЗ вже частково змінено, подальша помилка не відновить його попередній вміст.

## 12. Тригери й авторизація

`setup()` видаляє доступні поточному акаунту тригери лише для точних handler names:

- `WR_runDailyTransfer_v1`;
- `WR_installedOnEdit_v1`.

Після цього створює:

- `timeBased().everyDays(1).atHour(6)`;
- `forSpreadsheet(ss).onEdit()`.

Тригери інших акаунтів можуть залишатися невидимими й активними. Автор тригера повинен мати постійний доступ до майстер-таблиці та зовнішніх ТЗ.

Часовий тригер орієнтується на часовий пояс Apps Script, а дата в алгоритмі — на часовий пояс таблиці. Їх потрібно узгодити.

## 13. Блокування, журнал і відмовостійкість

`withDocumentLock_()` використовує `LockService.getDocumentLock()` і чекає до 30 секунд. Це не блокує ручні редагування користувачів і записи інших застосунків.

Операції над кількома листами та файлами не утворюють одну транзакцію. Можливі часткові результати, наприклад:

- частина рядка скопійована, але статус або дата не встановлені;
- ТЗ оформлено, але статус «Морди» не оновлено;
- новий лист створено, але конкретний кандидат завершився помилкою.

Після помилки перед повтором потрібно звірити фактичний стан рядка, ТЗ і журнал.

`_Warranty log` створюється автоматично, має заголовки `Timestamp`, `Type`, `Sheet`, `Row`, `Message` і приховується під час кожного звернення до журналу.

## 14. Відомі обмеження

- Немає dry-run або preview.
- Немає запуску для одного вибраного рядка.
- Пошук повтору обмежений цільовим гарантійним листом.
- Частково записаний рядок не ремонтується автоматично.
- Назви місяців не містять року.
- Новий лист наслідує найближчий доступний шаблон за номером місяця або останній лист книги.
- Щоденний перенос пропускає приховані «Морди».
- Ручна фіналізація використовує перший лист зовнішнього ТЗ й ігнорує `gid`.
- Зелений колір визначається пороговою RGB-евристикою, а не конкретним набором дозволених кольорів.
- onEdit не створює резерв текстів, не перевіряє посилання й не оновлює клієнтський звіт.
- Записи статусу через API не викликають installed onEdit так само, як ручне редагування користувачем.
- Масова вставка кількох клітинок навмисно ігнорується.
- Точний час запуску добового тригера не гарантується.

## 15. Перевірка перед випуском

1. Переконатися, що канонічний файл має назву `Code.gs`.
2. Виконати статичну перевірку синтаксису JavaScript.
3. Переглянути `git diff --check`.
4. На тестовій копії таблиці перевірити:
   - рядок до `deadline + 14` не переноситься;
   - придатний батьківський рядок переноситься;
   - `/1` або `/2` пропускається;
   - дубль того самого Google file ID не створюється;
   - місяць визначається дедлайном;
   - новий гарантійний лист створюється з шаблону;
   - `End data` дорівнює дедлайну + 21;
   - помилка одного кандидата не зупиняє наступні;
   - одиночне ручне `Перечек готово` запускає резервний onEdit;
   - масова вставка статусів ігнорується;
   - note і `_Warranty log` містять очікувану помилку.
5. Перевірити обидва тригери й останні виконання.
6. Зафіксувати зміни комітом і відправити їх до `origin/main`.
